# Phase 1 — Data Model

PostgreSQL 15 schema for SENAM API. All tables in schema `public`. Conventions:

- Primary keys are `uuid` generated by `gen_random_uuid()` from `pgcrypto`, unless otherwise noted.
- Timestamps are `timestamptz`. Every entity has `created_at`, `updated_at`. Soft-delete is `deleted_at` (nullable) — only used where called out.
- Money is `bigint` minor units in QAR (e.g., `1500` = 15.00 QAR). A `currency` column is **not** added in MVP; we only support QAR.
- All FKs are `ON DELETE RESTRICT` unless an explicit cascade is documented.
- Indexes called out below are the **non-obvious** ones — PKs and FKs always get an index implicitly.

```text
                       ┌────────────┐
                       │   users    │
                       └─────┬──────┘
                             │
              ┌──────────────┼──────────────────────────┐

       │ addresses  │  │ favorites │             │   orders    │◄────────┐
```

## 1. `users` — end customers

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `email` | citext UNIQUE NOT NULL | identity credential (FR-001) |
| `email_verified_at` | timestamptz | set on first successful OTP verification |
| `display_name` | text | |
| `phone` | text NULL | optional contact field (FR-001a), E.164 format |

- `CHECK (status IN ('active','banned','deleted'))`

**Deletion semantics (FR-036)**: account deletion **anonymises** rather than deletes — `email` is replaced by a hashed tombstone, `display_name` cleared, `phone` cleared, `status='deleted'`, `deleted_at` set. Orders, payments, reviews remain pointing at this row.

## 11. `slot_templates` and 12. `time_slots`

**slot_templates** define the grid (FR-009):

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `company_id` | uuid FK → companies(id) | |
| `slot_duration_minutes` | integer NOT NULL DEFAULT 60 | per R6 default |
| `capacity_per_slot` | integer NOT NULL DEFAULT 2 | |
| `weekday_mask` | smallint NOT NULL DEFAULT 0b1111101 | bitmask Sun..Sat (Friday off by default) |
| `open_time` | time NOT NULL DEFAULT `'08:00'` | |
| `close_time` | time NOT NULL DEFAULT `'22:00'` | |
| `effective_from` | date NOT NULL | |
| `effective_to` | date NULL | |

**time_slots** are materialised one row per concrete slot per day:

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `company_id` | uuid FK → companies(id) | |
| `slot_start_at` | timestamptz NOT NULL | |
| `slot_end_at` | timestamptz NOT NULL | |
| `capacity_total` | smallint NOT NULL | from template at generation time |
| `capacity_remaining` | smallint NOT NULL | atomic decrement on order create |

**Constraints / indexes / atomicity**:
- `UNIQUE (company_id, slot_start_at)` — prevents duplicate generation.
- `CHECK (capacity_remaining >= 0 AND capacity_remaining <= capacity_total)`.
- The slot-decrement (FR-009 + SC-005) is performed as a single SQL statement:
  ```sql
  UPDATE time_slots
     SET capacity_remaining = capacity_remaining - 1
   WHERE id = :slot_id
     AND capacity_remaining > 0
   RETURNING id;
  ```
  If 0 rows are returned, the slot is full and the booking fails atomically. No application-level lock is needed.
- Slots are generated nightly (next 14 days) by a BullMQ scheduled job, plus on-demand when a customer queries availability for a date no slot row exists yet for.

| `total_cap` | integer NULL | NULL = unlimited |
| `per_user_cap` | integer NULL | |

| `used_count` | integer NOT NULL DEFAULT 0 | atomically incremented |
| `is_active` | boolean NOT NULL DEFAULT true | |

**coupon_usages**:

| Column | Type | Notes |
|---|---|---|
| `coupon_id` | uuid FK → coupons(id) | |
| `user_id` | uuid FK → users(id) | |
| `order_id` | uuid FK → orders(id) | |
| `created_at` | timestamptz | |
| `PRIMARY KEY (coupon_id, order_id)` | | one usage per coupon per order |

**Index**: `CREATE INDEX coupon_usages_coupon_user ON coupon_usages(coupon_id, user_id);`

**Atomicity (FR-011, SC-005)**:
```sql
WITH cap AS (
  UPDATE coupons SET used_count = used_count + 1
   WHERE id = :coupon_id
     AND (total_cap IS NULL OR used_count < total_cap)
     AND is_active = true
     AND now() BETWEEN valid_from AND valid_until
  RETURNING id
)
INSERT INTO coupon_usages (coupon_id, user_id, order_id)
SELECT id, :user_id, :order_id FROM cap;
```
Combined with a separate `per_user_cap` check (one SELECT-COUNT inside the same transaction), this prevents over-redemption even under 100× concurrent contention.

| `coupon_id` | uuid NULL FK → coupons(id) | |

| `confirmed_at`, `accepted_at`, `started_at`, `completed_at`, `cancelled_at` | timestamptz NULL | event timestamps |

**Status lifecycle (FR-016, FR-015)**:
```
pending  ─ provider accepts ─►  accepted  ─►  on_the_way  ─►  arrived  ─►  in_progress  ─►  completed
   │                                │                │             │             │
   │                                ▼                ▼             ▼             ▼
   ├─ 5-min timeout → re-dispatch  cancelled (customer / admin / policy-based)
   │
   └─ after 3 attempts → unassignable (auto-refund)
```

A separate `order_status_history(order_id, from_status, to_status, actor_kind, actor_id, reason, at)` table records every transition (FR-032 traceability).

**Indexes**:
- `CREATE INDEX orders_customer_status ON orders(customer_id, status);`
- `CREATE INDEX orders_company_status ON orders(company_id, status);`
- `CREATE INDEX orders_completed_at ON orders(completed_at);` — drives report aggregates.

**Transitions are enforced in code** (transition matrix in the service) and double-checked by:
```sql
UPDATE orders SET status='accepted', accepted_at=now()
 WHERE id=:order_id AND status='pending';
```
returning zero rows → the transition is illegal at the DB layer (FR-016).

## 19. `settlements` and 20. `settlement_lines`

**settlements**:

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `company_id` | uuid FK → companies(id) | |
| `window_start`, `window_end` | timestamptz NOT NULL | the Sunday–Saturday window in Asia/Qatar |
| `opening_carry_forward` | bigint NOT NULL DEFAULT 0 | from previous negative settlement |
| `gross_online` | bigint NOT NULL | sum of completed online orders' total |
| `commission_online` | bigint NOT NULL | |
| `refunds_in_window` | bigint NOT NULL | |
| `commission_cod` | bigint NOT NULL | |
| `net_amount` | bigint NOT NULL | can be negative |
| `status` | text NOT NULL | `due` (SENAM pays), `provider_owes`, `paid`, `void` |
| `payout_reference` | text NULL | bank transfer ref when paid |
| `created_at`, `updated_at` | timestamptz | |
| `UNIQUE (company_id, window_start)` | | idempotency for the job |

`net_amount = gross_online − commission_online − refunds_in_window − commission_cod + opening_carry_forward`.

If `net_amount < 0`, status becomes `provider_owes`, and the next window's `opening_carry_forward` picks up the absolute value (carried as a negative).

**settlement_lines** is a denormalised join showing every accrual & refund included, for the downloadable statement PDF — derived from `commission_accruals` and `refunds`, no new authoritative data.

## 30. `otp_codes` (Redis, not Postgres)

OTP codes live exclusively in Redis. Key: `otp:{email}`. Value: `{bcrypt_hash, expires_at, attempts}`. TTL set to 10 minutes. Per-email and per-IP rate-limit counters are separate keys with their own TTLs (R5).

## Cross-cutting concerns the schema bakes in

- **Time-zone correctness**: every timestamp is `timestamptz` (stored as UTC); the settlement job computes window boundaries with `AT TIME ZONE 'Asia/Qatar'` to honour the Sunday cut-over (PRD §9.2).
- **PCI compliance**: no `card_*` columns anywhere; the only payment-related data we persist is the gateway's own `payment_id`.
- **Arabic content**: every user-facing text column is plain `text` with the database `lc_collate` set to a UTF-8 locale; we do not lower-case Arabic strings in WHERE clauses (Arabic doesn't have case).
- **Audit completeness**: every admin write goes through a service method decorated by `@AuditAction(...)`, which insert the `audit_logs` row inside the same transaction as the mutation (FR-024).
- **Soft delete vs retention (FR-036)**: only `users` and `company_users` are soft-deleted (with anonymisation). Orders, payments, settlements, audit_logs are immutable for retention.
