# Quickstart — SENAM API

This is the smoke-test path: clone, install, start the supporting services, run the API, exercise the first-booking happy path end-to-end. The full module-by-module implementation order lives in `tasks.md` (generated by `/speckit.tasks`).

## Prerequisites

- Node.js 20 LTS
- Docker + Docker Compose
- (Optional, for IDE convenience) `pnpm` — but `npm` works.

## 1. Get the code

```bash
# From the workspace root (C:\Users\zezo\Desktop\work\SENAM)
git checkout 001-senam-backend-api      # this feature branch
# The senam_api/ directory does not exist yet — it will be scaffolded
# during the first implementation tasks (see tasks.md once generated).
cd senam_api
```

## 2. Bootstrap dependencies

```bash
cp .env.example .env
npm install
docker compose -f docker-compose.dev.yml up -d   # postgres + redis + minio (S3) + mailhog (email sink)
npm run migration:run                            # apply TypeORM migrations
npm run seed:dev                                 # idempotent seed (see research.md R10)
```

Expected services after this step:

| Service | URL | Purpose |
|---|---|---|
| API | `http://localhost:3000` | NestJS app |
| Swagger UI | `http://localhost:3000/swagger` | Live API docs (non-prod only) |
| Postgres | `localhost:5432` | DB (user `senam` / db `senam`) |
| Redis | `localhost:6379` | OTP, cache, BullMQ |
| Minio (S3) | `http://localhost:9001` | object storage console |
| Mailhog | `http://localhost:8025` | catches outbound email — your OTP codes will appear here in dev |

## 3. Run the API

```bash
npm run start:dev
```

Confirm:
- `GET http://localhost:3000/healthz` returns `{ "status": "ok" }`.
- `GET http://localhost:3000/swagger` renders the OpenAPI UI with every endpoint listed in `contracts/openapi.yaml`.

## 4. Smoke test — customer first booking (happy path)

Each step below is a single `curl` (replace `$TOKEN` with the value returned by the previous step). The seed already created `customer1@test.com` as a fixture customer; you can also use a fresh email and follow the OTP via Mailhog.

```bash
# 4.1 — Request OTP
curl -sX POST http://localhost:3000/v1/auth/otp/request \
  -H 'content-type: application/json' \
  -d '{"email":"customer1@test.com","principal":"customer"}'
# → 200 OK  { "message": "otp_sent" }

# 4.2 — Grab the code from Mailhog (http://localhost:8025) — say it's 123456
curl -sX POST http://localhost:3000/v1/auth/otp/verify \
  -H 'content-type: application/json' \
  -d '{"email":"customer1@test.com","principal":"customer","code":"123456"}'
# → { "accessToken":"...","refreshToken":"...","principal":"customer","roles":[] }

export TOKEN=...

# 4.3 — List nearby companies (seed: 1 active car-wash in Doha)
curl -s "http://localhost:3000/v1/companies?categoryId=$CARWASH&sort=nearest&lat=25.2854&lng=51.5310" \
  -H "authorization: Bearer $TOKEN"
# → 200 OK with one company

# 4.4 — Fetch its services and pick one
curl -s "http://localhost:3000/v1/companies/$COMPANY_ID/services" -H "authorization: Bearer $TOKEN"

# 4.5 — Fetch slots for tomorrow
curl -s "http://localhost:3000/v1/companies/$COMPANY_ID/slots?date=$TOMORROW" -H "authorization: Bearer $TOKEN"

# 4.6 — Save an address (or use the seeded one)
curl -sX POST http://localhost:3000/v1/me/addresses \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"label":"Home","line":"شارع المرقاب، الدوحة","location":{"lat":25.2854,"lng":51.5310}}'

# 4.7 — Create the booking (COD to avoid touching the payment gateway in smoke test)
curl -sX POST http://localhost:3000/v1/bookings \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d "{
    \"companyId\":\"$COMPANY_ID\",
    \"services\":[{\"companyServiceId\":\"$SVC_ID\",\"quantity\":1}],
    \"slotId\":\"$SLOT_ID\",
    \"addressId\":\"$ADDR_ID\",
    \"paymentMethod\":\"cod\"
  }"
# → 201 Created — { id, status: "pending", ... }
```

If step 4.7 returns 201 with `status: "pending"` and the slot's `capacity_remaining` has decremented by 1 in Postgres, the customer happy path is wired.

## 5. Smoke test — provider accepts and completes

The seeded company has an owner login at `owner@nadhif.qa` (company slug: `nadhif`).

```bash
# Login as the provider
# (request + verify OTP as in 4.1–4.2 with principal=provider) → $PROVIDER_TOKEN

curl -s http://localhost:3000/v1/provider/me/orders?status=pending \
  -H "authorization: Bearer $PROVIDER_TOKEN"

curl -sX POST http://localhost:3000/v1/bookings/$ORDER_ID/status \
  -H "authorization: Bearer $PROVIDER_TOKEN" -H 'content-type: application/json' \
  -d '{"to":"accepted"}'

# Advance through the lifecycle
for to in on_the_way arrived in_progress completed ; do
  curl -sX POST http://localhost:3000/v1/bookings/$ORDER_ID/status \
    -H "authorization: Bearer $PROVIDER_TOKEN" -H 'content-type: application/json' \
    -d "{\"to\":\"$to\"}"
done
```

At the end:
- The order's `status='completed'` and `completed_at` is set.
- A `commission_accruals` row exists with `kind='cod'` for the COD path.
- Subscribing the customer's Socket.io client to `order:$ORDER_ID` should have surfaced every status change in real time (verify with `wscat -c ws://localhost:3000 ...`).

## 7. Smoke test — dispatch timeout

To verify FR-015 without waiting 15 minutes, the seed includes a feature flag `DISPATCH_ATTEMPT_TIMEOUT_MS` overridable via env. Set it to `5000` (5 seconds), create a booking against a company whose owner is not logged in, and watch:

1. After 5 seconds, the order's `dispatch_attempt` increments to 2 and a new provider is offered.
2. After 15 seconds (three attempts), the order transitions to `unassignable`, a refund row is created (or commission_accrual reversed for COD), and an admin-dashboard alert is emitted.

## 8. Running the test suites

```bash

npm run test:contract      # Supertest against an in-memory Nest app
npm run test:integration   # Testcontainers — real Postgres + Redis
```

The integration tier is the one that exercises the SC-005 invariants (no double-booking, no over-redemption, exactly-one accept under 100× concurrent requests).

## 9. Common troubleshooting

| Symptom | Probable cause | Fix |
|---|---|---|
| OTP email never appears in Mailhog | API can't reach Mailhog | check `MAIL_HOST=mailhog` in `.env`, confirm the service is up in `docker compose ps` |
| `relation "users" does not exist` on first run | Migrations not applied | `npm run migration:run` |
| Slot capacity stays at 2 after a booking | The order was rolled back due to a downstream failure (payment, coupon) — by design | look at the API logs and the `audit_logs` row for the failed `booking.create` correlation id |
| Provider socket never receives status updates | JWT not passed in handshake | set `socket.io` `auth: { token: $TOKEN }` on the client; cross-check with the gateway's logs |
| `Slot is not available` even though it looks empty | Slot row hasn't been generated yet | hit `GET /companies/:id/slots?date=...` once — it generates on demand for unseen dates |
