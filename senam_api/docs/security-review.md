# SENAM API — Security Review

**Date**: 2026-05-20  
**Scope**: SENAM Backend API — all endpoints in `specs/001-senam-backend-api/contracts/openapi.yaml`  
**Framework**: OWASP API Security Top 10 (2023) + platform-specific checks

---

## OWASP API Security Top 10 (2023)

### API1: Broken Object Level Authorisation

**Risk**: A customer modifies another customer's booking or address by guessing a UUID.

**Controls implemented**:
- Every customer-facing query includes a `WHERE user_id = :currentUserId` clause (e.g., `GET /v1/bookings`, `GET /v1/me/addresses`).
- Provider endpoints scope queries to `company_id` loaded from the JWT claim (`companyId`).
- Admin endpoints require a valid role from `admin_users`; there is no elevation path from customer/provider JWT to admin.
- TypeORM repositories injected into services always filter by the authenticated subject — never by a raw user-supplied ID without cross-checking ownership.

**Residual risk**: LOW. UUIDs are generated by `gen_random_uuid()` (pgcrypto) — not sequential, not guessable.

---

### API2: Broken Authentication

**Risk**: An attacker bypasses the OTP flow or forges a JWT.

**Controls implemented**:
- OTP codes are 6-digit numeric; bcrypt-hashed (`cost=10`) before storing in Redis — the Redis dump cannot be replayed.
- Issuance rate-limited: **3 OTP requests per email per hour** (via Redis `INCR`+`EXPIRE`).
- Verification rate-limited: **5 attempts per issued code** before the code is invalidated.
- OTP TTL: **10 minutes** (Redis key expiry — single-use enforced by `DEL` after first successful verify).
- JWT access tokens: 15-minute TTL, signed HS256 with a ≥ 64-character secret.
- Refresh tokens: 30-day TTL, stored as a bcrypt hash in Redis keyed by token ID; rotated on every refresh call.
- The `sub`, `principal`, and `roles` claims are extracted from the verified JWT, never from the request body.

**OTP brute-force analysis**:
- Entropy: 10^6 codes with 5 attempts → probability of guessing = 5 × 10^-6 per window.
- Issuance rate limit makes targeted enumeration ≈ 3 codes/hour/email.
- Combined: an attacker targeting a single email can try ≤ 15 codes per hour — effectively negligible for a 6-digit space.

**Residual risk**: LOW.

---

### API3: Broken Object Property Level Authorisation

**Risk**: A customer sends a request body with unexpected admin-only fields (e.g., `status`, `commissionBps`).

**Controls implemented**:
- `ValidationPipe` is configured with `whitelist: true` and `forbidNonWhitelisted: true` globally — any property not declared in the DTO is stripped or rejected before reaching the controller.
- DTOs are separate per role (e.g., `UpdateMeDto` does not include `status`; only `Admin.UpdateCompanyDto` includes `commissionBps`).

**Residual risk**: LOW.

---

### API4: Unrestricted Resource Consumption

**Risk**: An attacker hammers the OTP endpoint or slots endpoint with thousands of requests.

**Controls implemented**:
- Global `ThrottlerModule`: 100 requests per minute per IP (configurable, applies to all endpoints).
- OTP-specific throttle: 3 issuances per email per hour (Redis-backed, survives replicas).
- The `POST /bookings` endpoint is guarded by the slot's `capacity_remaining ≥ 0` DB constraint — even under burst, only valid capacity is consumed.
- Large list endpoints (`/v1/companies`, `/v1/admin/orders`) use cursor-based pagination with a configurable `limit` (default 20, max 100).

**Residual risk**: MEDIUM. No per-user global rate limit is currently enforced beyond the global IP-based throttle. Recommendation: add a per-authenticated-user rate limit layer for critical mutating endpoints in a follow-on task.

---

### API5: Broken Function Level Authorisation

**Risk**: A provider calls an admin-only endpoint.

**Controls implemented**:
- `JwtAuthGuard` is applied globally; all public endpoints must opt out with `@Public()`.
- `RolesGuard` is applied globally; endpoint-specific roles are enforced via `@Roles(...)` decorator.
- Admin endpoints under `/v1/admin/*` require `@Roles('super_admin', 'ops_admin', ...)` at the controller or method level.
- The `principal` claim in the JWT (`customer`, `provider`, `admin`) determines which user table was used for authentication; a provider JWT cannot satisfy an `admin` role check.
- Staff endpoints (`/v1/provider/me/orders/:id/assign`) validate that the staff user belongs to the same `company_id` as the JWT's `companyId` claim.

**Residual risk**: LOW. Each new endpoint must apply `@Roles()` explicitly; a future endpoint added without `@Roles()` would still be protected by `JwtAuthGuard` but accessible to any authenticated user. Recommendation: add a lint/test rule that flags undecorated controller methods.

---

### API6: Unrestricted Access to Sensitive Business Flows

**Risk**: An attacker books the same slot 1 000 times in parallel, exhausting capacity before legitimate customers can book.

**Controls implemented**:
- Slot decrement uses a single-statement atomic `UPDATE time_slots SET capacity_remaining = capacity_remaining - 1 WHERE id = :id AND capacity_remaining > 0 RETURNING id` — the DB `CHECK (capacity_remaining >= 0)` is a safety net.
- Coupon application uses the same atomic CTE pattern; `coupons.used_count` cannot exceed `total_cap`.
- The `POST /bookings` endpoint is not exempt from the global throttle.
- SC-005: integration tests assert that 200 concurrent bookings against a single-capacity slot yield exactly **one** success and 199 × 409 responses.

**Residual risk**: LOW for correctness. An attacker can still trigger many failed booking attempts; the throttle limits this but doesn't prevent determined DDoS. Production mitigation: WAF rate-limiting at the infrastructure layer.

---

### API7: Server Side Request Forgery (SSRF)

**Risk**: An attacker supplies a malicious URL in a presigned-upload callback.

**Controls implemented**:
- The API never fetches user-supplied URLs. All external calls are to pre-configured endpoints (MyFatoorah, SES, R2) loaded from validated env vars.
- Presigned URLs are generated by the backend (with fixed S3 bucket and key prefix); the client only receives the URL, it does not supply one.
- Webhook endpoint (`/v1/payments/webhook/myfatoorah`) accepts only POST bodies — no URL redirection is triggered.

**Residual risk**: LOW.

---

### API8: Security Misconfiguration

**Risk**: Swagger UI exposed in production; debug logging enabled; JWT secret too short.

**Controls implemented**:
- Swagger UI is conditionally mounted: `if (process.env.NODE_ENV !== 'production')` — only exposed in dev/staging.
- `ConfigModule` validates all env vars on startup via `class-validator`; the app refuses to start if `JWT_SECRET` is missing or < 32 chars (enforce 64+ chars via the validator).
- Pino logger redacts `authorization`, `password`, and `card_*` fields from all log output.
- `X-Powered-By` header is not sent (NestJS/Express default).
- CORS should be configured for the specific app origins in production (currently set to all origins in development — review `main.ts` before production).

**Residual risk**: MEDIUM. CORS configuration has not been explicitly locked down for production. **Action required**: configure `app.enableCors({ origin: [...allowedOrigins] })` in `main.ts` before the first production deployment.

---

### API9: Improper Inventory Management

**Risk**: Old API versions remain accessible after a version bump.

**Controls implemented**:
- The API uses a single `/v1` prefix. There is no `/v0` or legacy routing.
- The Swagger UI shows the live endpoint surface; deprecated endpoints are not currently present.
- The congruence test (T101) ensures spec and live doc stay in sync, which indirectly flags stale endpoints.

**Residual risk**: LOW for MVP. Recommendation: when v2 endpoints are added, explicitly retire v1 routes with `410 Gone` and document the sunset date.

---

### API10: Unsafe Consumption of APIs

**Risk**: A malicious MyFatoorah webhook payload compromises the system.

**Controls implemented**:
- The `POST /v1/payments/webhook/myfatoorah` endpoint verifies the HMAC signature (`MYFATOORAH_WEBHOOK_SECRET`) before processing any payload data.
- The webhook handler is a `@Public()` endpoint — JWT authentication is intentionally skipped for gateway callbacks.
- All webhook payload fields are parsed through `class-validator` DTOs; unknown fields are stripped.
- Payment status is confirmed against the `PaymentPort.verifyWebhook` method which re-fetches the payment status from MyFatoorah's API before updating the local record.

**Residual risk**: LOW.

## Platform-specific concerns

### JWT secret rotation procedure

1. Generate a new secret (≥ 64 chars of cryptographic randomness): `openssl rand -hex 64`.
2. Deploy a version of the API that accepts **both** old and new secrets (dual-key verification — add to `TokensService`).
3. Wait one access-token TTL (15 minutes) for all old tokens to expire.
4. Remove the old secret from the codebase and re-deploy.
5. Force-revoke all refresh tokens (flush the `refresh:*` keyspace in Redis) to invalidate sessions.

### Refresh token revocation under compromise

If a refresh token is compromised:
1. The token ID is the first part of the `tokenId.rawBytes` format. Extract it.
2. Call `DEL refresh:<tokenId>` in Redis to immediately revoke it.
3. If the full Redis keyspace is suspected: `SCAN 0 MATCH refresh:* COUNT 10000` and delete all matching keys — this forces all users to re-authenticate.
4. Rotate the JWT secret (see above).

### Presigned-URL expiry windows

| Purpose          | TTL       | Rationale                                      |
|------------------|-----------|------------------------------------------------|
| KYC document upload | 15 min | Short window; sensitive; single-use expected   |
| Gallery image upload | 30 min | Typical upload session + network latency margin |
| Gallery image read  | 24 h   | Public-facing, cacheable; R2's public CDN preferred in production |
| Review photo read   | 1 h    | Contextual; doesn't need to be cached long      |

All presigned URLs are HTTPS. Bucket policies deny unauthenticated access to the raw object path.

### Rate-limit headroom

| Limit                          | Value            | Redis key pattern           |
|--------------------------------|------------------|-----------------------------|
| OTP issuance                   | 3 / email / hour | `otp:rate:issue:{email}`    |
| OTP verification attempts      | 5 / code         | `otp:rate:verify:{email}`   |
| Global API throttle            | 100 req / min / IP | NestJS ThrottlerModule      |
| Booking creation (slot guard)  | n/a (DB-enforced)| DB `capacity_remaining ≥ 0` |

Current headroom for legitimate power users (3 OTP requests/hour) is conservative; review if password-less daily login is required.

## Recommendations summary

| Priority | Action                                                                               |
|----------|--------------------------------------------------------------------------------------|
| HIGH     | Lock CORS to specific app origins before production deployment                       |
| HIGH     | Confirm JWT_SECRET length enforcement in `env.schema.ts` (≥ 64 chars)               |
| MEDIUM   | Add per-authenticated-user rate limiting for `POST /bookings` and `POST /auth/*`     |
| MEDIUM   | Add a lint rule flagging controller methods without explicit `@Roles()` or `@Public()`|
| LOW      | Add WAF-level rate limiting in front of the API (Cloudflare, AWS WAF)                |
| LOW      | Enable `HSTS` header in production (`Strict-Transport-Security: max-age=31536000`)   |
| LOW      | Review and limit max payload size (`app.use(express.json({ limit: '1mb' }))`)        |
